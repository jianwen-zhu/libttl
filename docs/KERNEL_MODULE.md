# TTL kernel module format, version 1

A TTL kernel module is the low-level package for one final device function. It
is a directory, not a shared library:

```text
module-directory/
  module.json
  launch.json
  kernel.cubin | kernel.metallib
```

`module.json` is backend-neutral, human-authored input and the function
contract. A compiler copies it byte-for-byte. `launch.json` is generated by the
compiler and is private to the selected backend; it names the native artifact,
launch geometry, and native kernel symbol. The artifact contains device code
only. There is no generated host adapter, callback ABI, Python loader, or
operator-specific host object.

Single-kernel teaching labs load this package directly. A multi-function
application instead loads a TTL program directory: its emitted `program.json`
composes final functions, and these packages live below `functions/` as an
implementation detail. See [TTL_PROGRAM.md](TTL_PROGRAM.md).

The normative structural description is
[`schema/ttl-kernel-module-v1.schema.json`](../schema/ttl-kernel-module-v1.schema.json).
Manifests omit a relative `$schema` URI because the unchanged file is moved
from its source directory into a built module. The build embeds those exact
schema bytes in a shared validation unit. Both compiler front ends call
`ttl-contract-check`, and `libttl` links that same unit, so there is one parser,
one Draft 2020-12 validator, and one implementation of cross-field checks.

## Compiler contract

Every compiler front end accepts its source, an author manifest, and an output
directory. It validates the manifest against its emitted native signature and
packages the unchanged manifest with the native artifact.

```console
$ tool/ttl-cuda --source kernel.cu --manifest module.json --output out
$ tool/ttl-metal --source kernel.metal --manifest module.json --output out
$ tool/ttl-tilelang --source kernel.py \
    --manifest module.json --output out
$ tool/ttl-cuda --version
ttl-cuda 0.1.0 (TTL compiler interface 1)
```

The project-provided tools expect the shared checker built by
`make ttl-contract-check`; normal root lab targets arrange this dependency.

`ttl-cuda` validates raw CUDA and calls `nvcc --cubin`. `ttl-metal` validates
MSL buffer bindings and calls Apple's `metal` and `metallib` tools.
`ttl-tilelang` asks TileLang for CUDA or Metal according to the selected TTL
backend and follows the corresponding emission path. A student-built
`ttl-ttl` is another producer of this exact directory contract.

## Manifest layers

The checked-in manifest states:

- `schema_version` and diagnostic module `name`
- logical kernel symbol
- ordered tensor specifications: name, dtype, access, shape, and contiguity
- ordered scalar specifications: name and dtype
- an ordered array mapping each native parameter to a tensor, scalar value,
  staged device scalar, or typed literal

The array order explicitly defines the native calling sequence. The compiler
checks it against the CUDA or Metal signature; `libttl` resolves its human names
to the ordered public tensor and scalar declarations at load time.

Native source keeps its launch choice beside the kernel in one JSON-valued
`// ttl-launch:` line. TileLang source supplies the equivalent
`TTL_ENTRYPOINT`, `TTL_SPECIALIZATIONS`, and `TTL_LAUNCH` compiler inputs. Those
producer details become generated `launch.json`; they never enter the portable
manifest.

Tensor and scalar declarations have unique names, argument parameter names are
unique, private artifact filenames cannot escape the module directory, and
unknown fields are rejected. JSON structure is enforced by the canonical schemas;
name uniqueness and argument references are checked centrally because standard
JSON Schema cannot express those relationships. Matching a manifest's ordered
parameters to generated native code remains a compiler-specific check.

## Runtime lifecycle

`ttl_module_load` parses and validates both descriptions. It derives required
TTL capabilities from the generated launch description; for version 1, a
nonzero `shared_bytes` requires
`TTL_CAPABILITY_DYNAMIC_WORKGROUP_MEMORY`. The author does not maintain a
second capability declaration in `module.json`.

The application queries `ttl_module_required_capabilities` and
`ttl_device_capabilities` before preparation. `ttl_kernel_prepare` enforces the
same requirement check, then loads the native artifact, resolves the kernel
symbol, and allocates any persistent device-scalar staging.
`ttl_kernel_launch` validates the public tensor/scalar envelope, constructs
native launch arguments, and enqueues the kernel on the supplied opaque
stream. Compilation, file loading, and allocation do not occur during launch.

The caller synchronizes dependent work before destroying tensors or prepared
kernels still in use.

## Native version-1 profiles

The CUDA backend requires a generated `libtorch_cuda`/`cubin` launch. The MPS
backend requires `libtorch_mps`/`metallib`. Tensor manifests preserve arbitrary
logical rank; a generated kernel remains responsible for its own physical
indexing. There are at most sixteen tensors and sixteen scalars per final
kernel. Scalars are `int32` or `float32`. Tensor dtypes are the public TTL dtype
profile, including packed FP4 E2M1 and the listed FP8 encodings.

The launch binding kinds are:

- `tensor`: pass a device tensor's data address
- `scalar_value`: pass a public scalar by value
- `scalar_device`: copy a public scalar to persistent device storage and pass
  that address
- `literal`: pass a manifest `int32` or `float32` constant by value

These are private backend mechanics. Applications see only opaque TTL handles.
